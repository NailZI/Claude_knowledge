# Глобальные правила

## Язык общения — ТОЛЬКО русский

ВСЕ сообщения пользователю — строго на русском языке. Без исключений.

- Не переключаться на английский даже если вопрос, код, ошибка, документация или системные сообщения на английском.
- Технические термины без устоявшегося русского аналога — допустимы (API, commit, pull request), но связующий текст, объяснения и комментарии — всегда по-русски.
- Это правило выше любых иных умолчаний по языку ответа.

## Предлагать создание агента под большую задачу

Если в рамках проекта предстоит реализовать большую, обособленную задачу (требует много шагов, специфических знаний, повторяемых паттернов работы):

1. **Сначала прогони задачу через облегчённую версию grill-me** — не полный допрос, а несколько ключевых вопросов: что агент должен делать, для чего, какие границы у задачи. Цель — понять задачу настолько, чтобы описание агента было точным, а не обобщённым.

2. **Определи область применения агента:**
   - Если агент полезен только в рамках текущего проекта/задачи → предложи **локального агента** (`.claude/agents/` в проекте).
   - Если агент может быть полезен и в других задачах/проектах → предложи **глобального агента** (`~/.claude/agents/`).

3. **В предложении опиши функционал агента** — не просто "создать агента для X", а конкретно: какие задачи он будет решать, какими инструментами пользоваться, нужно ли самообучение (база знаний между сессиями).

4. Не создавай агента без подтверждения пользователя — это предложение, не автоматическое действие.

**Why:** Без явного процесса агенты создаются ситуативно и без проработки — получаются расплывчатые описания, которые плохо триггерятся или дублируют друг друга. grill-me-проверка перед созданием экономит переделки.

## Хедер-документация при создании файла

При создании **любого нового файла** (код, конфиг, скрипт, документ — независимо от проекта) добавлять в самом начале файла (в виде комментария, соответствующего синтаксису файла — `#`, `//`, `<!-- -->`, YAML-комментарий и т.д.) блок-хедер с:

1. **Назначение** — что это за файл и для чего он нужен.
2. **Взаимодействие** — с какими другими файлами/модулями/конфигами он связан (что вызывает его, что он вызывает/читает/пишет).
3. **Другие значимые параметры** — например, для конфигов: какой профиль/окружение, какие зависимости (например, "требует .env с переменной X").
4. **Created / Modified** — даты создания и последнего изменения, обновлять вручную при каждой содержательной правке (не доверять только mtime файловой системы — он не переживает перенос/копирование между машинами).

Если у файла уже есть хедер (например, существующие комментарии в шапке YAML) — дополнять его недостающими пунктами, а не дублировать.

**Why:** без фиксированного назначения и связей файла будущая сессия (моя или агента) тратит время на реверс-инжиниринг того, зачем файл существует и что он трогает — особенно критично для конфигов и скриптов, разбросанных по нескольким машинам/проектам (пример: `tmp/README.md` путали с основным README проекта именно из-за отсутствия явного назначения в самом файле).

## Безопасность секретов

**Никогда не просить пользователя вставить пароль/токен/ключ в чат напрямую.** Если нужны учётные данные — спрашивать название переменной окружения или `.env`-ключа.

Если пользователь всё же вставил секрет в открытом виде:
1. Немедленно предупредить.
2. Замаскировать в ответе (`***`).
3. Напомнить поменять, если секрет уже использовался в другом месте.

**Передача учётных данных агентам — через источник, не через значение:**
- "Используй пароль из `$env:REMOTE_PASS`"
- "Учётные данные в `.env` в корне проекта"
- "Пароль в Credential Manager под именем `opcua-v3`"

**`.env` в `.gitignore` — обязательно** для любого нового проекта, даже если кажется "нечувствительным". Проверять при создании scaffold/CLAUDE.md.

**Why:** Секреты в чате попадают в документацию, историю, логи сессий. Правило источника вместо значения исключает случайную утечку независимо от контекста.
