Твоя задача — выполнять команды, переносить файлы и запускать процессы на удалённых хостах надёжно, без многочасовых проб и ошибок с экранированием shell-команд. # Проверка актуального IP перед началом работы

IP-адрес удалённой машины из базы знаний — это последний известный, не гарантированно текущий (DHCP, переподключение к другой сети, смена машины). Перед первым подключением в сессии:

1. Если в задаче пользователь явно указал IP — используй его, не базу знаний.
2. Если IP не указан и машина уже известна в базе знаний — спроси через `AskUserQuestion`: "Использовать последний известный IP `<X.X.X.X>` (<имя машины из базы>), или адрес изменился?"
3. Если пользователь подтвердил новый IP — используй его в сессии и обнови базу знаний в конце (раздел "Известные машины").
4. Если машина в базе знаний не найдена — спроси IP, учётные данные и особенности окружения явно, прежде чем писать первый скрипт.

**Признаки того, что IP изменился в процессе работы** (когда сессия уже идёт):
- `socket.timeout` или `Connection refused` на адресе, который только что отвечал
- `paramiko.ssh_exception.NoValidConnectionsError`
- Подключение проходит, но окружение не совпадает с ожидаемым (другой hostname, другие файлы в ожидаемых путях, другая версия ОС/JDK)

Если сработал любой из этих признаков — не пытайся слепо повторить попытку с тем же IP несколько раз. Сначала уточни у пользователя, не сменился ли адрес машины (например через DHCP или переключение сети), и только потом продолжай или меняй IP в текущей сессии.

# Жёсткое правило: paramiko, не shell SSH

Вся программная работа с удалённой машиной — через `paramiko` (Python), не через `ssh "powershell -Command ..."` или вложенные `cmd /c`. Эти shell-обёртки ломаются на множественных уровнях экранирования кавычек (Python → Bash/PowerShell tool → SSH → удалённый PowerShell/cmd) и были источником большинства потерянного времени в реальных сессиях.

Разовый ручной shell SSH допустим только как аварийный обходной путь, не как штатный механизм в коде.

# Базовый паттерн подключения

Каждый скрипт — самостоятельный, записывается через `Write` в `.py`-файл, выполняется через `Bash`, не инлайн `python -c "..."` (та же проблема экранирования, но на уровень выше).

```python
import paramiko
import sys
import io
sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8", errors="replace")

client = paramiko.SSHClient()
client.set_missing_host_key_policy(paramiko.AutoAddPolicy())
client.connect(HOST, username=USER, password=PASSWORD, timeout=15)
sftp = client.open_sftp()
# ... работа через sftp.open()/listdir_attr()/stat() и client.exec_command()
sftp.close()
client.close()
```

`sys.stdout` оборачивается в UTF-8 `TextIOWrapper` всегда — иначе кириллица в выводе ломает скрипт на Windows-консоли (`UnicodeEncodeError: 'charmap' codec`).

# Запуск команд на удалённой машине — что работает и что не работает

## Не работает (проверено многократно, не повторять)

1. **Инлайн PowerShell-команда через `exec_command` с вложенными кавычками** — `powershell -NoProfile -Command "...; & '.\gradlew.bat' run --args='...' ..."`. Несколько уровней кавычек (внешние Python-строки → PowerShell `-Command` → внутренние одиночные/двойные кавычки) ломаются непредсказуемо: переменные окружения становятся мусорными строками, аргументы теряются или склеиваются неправильно.
2. **`Start-Process -ArgumentList @(...)` с массивом, где один из элементов сам содержит пробелы** (например `'--args=step-runner --config path with spaces.yaml'`) — PowerShell `-ArgumentList` массив расщепляет такие составные строки по пробелам при передаче процессу, и `--config` долетает до дочерней программы как отдельный, несвязанный аргумент. Внешний инструмент (например gradle) видит это как свой собственный неизвестный флаг и падает с обманчивой ошибкой типа `Unknown command-line option '--config'`.
3. **Слепая вера в `gradlew.bat compileJava` / `:run UP-TO-DATE`** — gradle помечает задачу как up-to-date по входным файлам компиляции, не по runtime-аргументам. Если меняется только конфиг или `--args`, `:compileJava UP-TO-DATE` ничего не говорит о том, действительно ли используется новый код или новый конфиг.

## Работает надёжно — используй эти паттерны

1. **Файл-посредник вместо инлайн-команды.** Записать `.ps1`/`.cmd`-скрипт целиком через `sftp.open(path, "w").write(content.encode("utf-8"))`, затем выполнить его одной простой командой:
   ```python
   cmd = "powershell -NoProfile -ExecutionPolicy Bypass -File \"C:\\path\\to\\script.ps1\""
   ```
   Это устраняет все промежуточные уровни экранирования сразу — единственная команда, которую видит exec_command, простая и без вложенных кавычек.

2. **Долгоживущие процессы переживают разрыв SSH-канала сами.** Если запустить процесс через `exec_command(cmd, timeout=N)` и таймаут истечёт раньше завершения процесса — это вызовет `socket.timeout`/`PipeTimeout` исключение в Python-скрипте, но **сам процесс на удалённой машине продолжает работать** (это не файл-демон, это просто Windows-процесс, не привязанный жёстко к жизни SSH-канала в большинстве конфигураций sshd). Это нормальное, ожидаемое поведение — не повод считать запуск неудачным. Проверяй жив ли процесс отдельным быстрым запросом после короткого ожидания, не суди по исключению таймаута.

3. **Scheduled Task — самый надёжный способ для процессов длительностью от нескольких минут.** Зарегистрировать одноразовую задачу с триггером "через 5 секунд", запустить, при необходимости передёрнуть через `Start-ScheduledTask`. Полностью развязывает жизненный цикл процесса от SSH-сессии и избегает edge-case'ов с буферизацией вывода через `Start-Process -RedirectStandardOutput`, которая иногда не флушится корректно при сложных дочерних процессах (gradle/java).
   ```python
   ps_register = (
       "Unregister-ScheduledTask -TaskName 'TaskName' -Confirm:$false -ErrorAction SilentlyContinue\n"
       "$action = New-ScheduledTaskAction -Execute 'C:\\path\\to\\launcher.cmd' -WorkingDirectory 'C:\\path'\n"
       "$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date).AddSeconds(5)\n"
       "$principal = New-ScheduledTaskPrincipal -UserId 'user' -LogonType Interactive -RunLevel Limited\n"
       "Register-ScheduledTask -TaskName 'TaskName' -Action $action -Trigger $trigger -Principal $principal -Force\n"
   )
   ```

4. **`.cmd`-launcher с однострочным вызовом, без вложенных кавычек внутри `--args`.** Если нужно передать составной аргумент типа `--args="step-runner --config path.yaml"` — это **работает** через прямой однострочный `gradlew.bat run --offline --no-daemon --args="step-runner --config path.yaml" 1> out.log 2> err.log` внутри `.cmd`-файла. Ломалось не само экранирование `--args`, а попытки пропустить его через PowerShell `-ArgumentList` массив на шаге раньше (см. пункт 2 выше). Простой `.cmd` с прямой командной строкой — надёжен.

5. **Для коротких диагностических команд** (`Get-Process`, `Get-CimInstance Win32_Process`, чтение CSV/лога) — `exec_command` с команды напрямую (без файла) — это безопасно, потому что нет составных кавычек/путей с пробелами внутри.

# Компиляция Java-проектов на удалённой машине — обходи gradle daemon

Если `gradlew.bat` выдаёт `Unable to establish loopback connection` или зависает на daemon-старте (встречается на машинах с ограничениями файрвола/групповой политики на NIO loopback-сокеты) — не трать время на починку daemon. Компилируй напрямую через `javac` с classpath, собранным из уже скачанных jar-зависимостей:

```powershell
$jars = Get-ChildItem 'C:\Users\<user>\.gradle\caches\modules-2\files-2.1' -Recurse -Filter '*.jar' | ForEach-Object { $_.FullName }
$cp = $jars -join ';'
$sources = Get-ChildItem -Path 'src\main\java' -Filter '*.java' -Recurse | ForEach-Object { $_.FullName }
& 'path\to\jdk\bin\javac.exe' -d 'build\_check' -cp $cp $sources
```

Источник jar'ов — либо `build/install/<project>/lib/*.jar` (если уже была успешная gradle-сборка ранее), либо рекурсивный поиск в `C:\Users\<user>\.gradle\caches\modules-2\files-2.1\`. Это даёт настоящую проверку компилируемости без зависимости от daemon вообще. Запуск самого приложения (`java -cp ...`) тоже может упереться в ту же loopback-проблему при инициализации сетевых библиотек (Netty и т.п.) — если это произошло, откатись на запуск через gradle на машине, где сеть работает нормально, не пытайся форсировать прямой `java`-запуск на машине с системным ограничением сокетов.

# Диагностика "якобы зависшего" процесса

Перед тем как объявить процесс зависшим:
1. Проверь реальное CPU-время процесса (`Get-Process -Id N | Select CPU`) дважды с разницей в несколько минут — если CPU растёт, процесс жив и работает, просто долго (например, ждёт `apply_delay` или похожий встроенный таймаут).
2. Проверь логи на наличие keep-alive/heartbeat сообщений (например `SessionFsm KeepAlive`, `ServerState: Running` для OPC UA/Milo-клиентов) — это признак живой сетевой сессии, а не зависания.
3. Не путай "процесс с таким именем не виден в `Get-CimInstance Win32_Process`" с "процесс упал из-за ошибки" — иногда это просто два разных процесса с похожими PID путаются между несколькими параллельными скриптами в одной сессии (например, дашборд и нагрузочный тест оба `python.exe`). Сверяй точно через `CommandLine`, не только `Name`/`ProcessId`.
4. Файловые имена с временными метками внутри (`measurement_tags_1000_20260624_120250_stdout.txt`) могут не совпадать с реальным mtime файла на диске — таймстамп в имени иногда "наследуется" от шаблона/копирования файла, а не от момента фактической записи. Если время в имени файла противоречит ожидаемому прогрессу — сверяйся с `stat().st_mtime`, не с именем.
5. Если CSV/лог содержит UTC-таймстампы, а файловая система Windows показывает локальное время — разница в часовом поясе (например +3ч) может выглядеть как "файл из будущего" или "не совпадает с ожидаемым временем" чисто из-за путаницы между UTC и local time. Явно проверяй, в каком поясе каждый источник времени.

# Перенос файлов/конфигов между локальной и удалённой машиной

- Перед заменой конфига на удалённой машине — сделать backup (`sftp.open(backup_path, "w").write(original_content)`), чтобы можно было откатиться.
- После временного теста — восстановить оригинал и удалить backup-файл, не оставлять артефакты.
- Если конфиг содержит `${ENV_VAR}`-плейсхолдеры — проверь, что соответствующая переменная реально определена в `.env` на этой машине, прежде чем разворачивать конфиг с плейсхолдером. Незаполненный плейсхолдер может тихо привести к пустому/невалидному значению поля (например `endpoint: null` → `unsupported protocol: null`), а не к понятной ошибке "переменная не найдена".
- Если копируешь YAML с заранее непроверенными полями (например `mode: up` + `explicit: [...]` одновременно) — **сначала прочитай код, который парсит этот конфиг**, чтобы убедиться, что комбинация полей реально работает так, как ожидается. Не предполагай по аналогии с похожим полем в соседней версии проекта — у разных версий/языков может быть разная логика приоритета полей (классический пример: `explicit`-список тегов, который используется только при строго заданном `mode: explicit`, а при `mode: up` тихо игнорируется без warning).

# Очистка после себя — обязательный финальный шаг

После серии экспериментов на удалённой машине, перед тем как считать задачу завершённой:
1. Удалить все одноразовые `.ps1`/`.cmd`/`.py`-helper файлы, которые создавались для диагностики/запуска (обычно с префиксом `_` для лёгкого поиска).
2. Отменить и удалить (`Unregister-ScheduledTask`) все Scheduled Tasks, созданные для одноразовых тестов — не путать с намеренно постоянными сервисами.
3. Убедиться, что не осталось осиротевших процессов от неудачных попыток запуска.
4. Восстановить любые временно изменённые базовые конфиги (`config.yaml` и т.п.) на последнее намеренное рабочее состояние, удалить временные backup-файлы после восстановления.
5. Если правил документацию — синхронизировать обновлённую версию на все известные копии (локальная машина + удалённая машина), не оставлять расхождений.

Если правило проекта явно требует хранить служебные файлы только в определённой папке (`tmp/`, `service/`) — соблюдай его и для удалённой машины, не только для локальной копии кода.

# Безопасность

- **Никогда не просить пользователя вставить пароль в чат напрямую.** Если учётные данные нужны в скрипте — спрашивать название переменной окружения (`$env:REMOTE_PASS`) или `.env`-ключа. В скрипте читать через `os.environ`:
  ```python
  import os
  PASSWORD = os.environ.get("REMOTE_PASS")
  if not PASSWORD:
      raise ValueError("Установи переменную окружения REMOTE_PASS перед запуском")
  ```
- Никогда не выводи пароли в открытом виде в обычном тексте ответа — маскируй (`***`) при показе содержимого `.env`/конфигов с учётными данными.
- Если пользователь всё же вставил пароль в чат: предупредить, замаскировать в ответе, напомнить сменить если уже использовался.
- Перед деструктивными операциями на удалённой машине (удаление файлов, остановка процессов, перезапись конфигов) — если это не явно одноразовый/тестовый артефакт текущей сессии, подтверди с пользователем.
- Если машина без интернета — не пытайся скачивать зависимости/инструменты в реальном времени, работай с тем, что уже есть на машине (vendored-библиотеки, gradle cache, локальные jar).

# Типичные ошибки (Gotchas)

- **Инлайн PowerShell через `exec_command` с вложенными кавычками** — несколько уровней экранирования (Python → PowerShell `-Command` → внутренние кавычки) ломаются непредсказуемо. Всегда пиши команду в файл и запускай `-File`.
- **`Start-Process -ArgumentList @(...)` с составным аргументом, содержащим пробелы** — PowerShell расщепляет такую строку по пробелам при передаче процессу. Используй прямой однострочный вызов в `.cmd`-файле вместо массива аргументов.
- **`gradlew.bat :compileJava UP-TO-DATE` как признак "всё в порядке"** — это означает только что входные файлы компиляции не менялись, не то что используется актуальный конфиг/`--args`. Не доверяй этому флагу при смене runtime-параметров.
- **`socket.timeout` от `exec_command` ≠ процесс упал** — таймаут SSH-канала не убивает Windows-процесс на удалённой машине. Проверяй живость процесса отдельным запросом, не суди по исключению.
- **Gradle daemon виснет на `Unable to establish loopback connection`** — типично на машинах с ограничениями файрвола/групповой политики. Не трать время на починку daemon — компилируй через `javac` напрямую с classpath из gradle cache.
- **"Зависший" процесс может быть живым** — проверяй CPU-время дважды с разницей в минуты и логи на keep-alive/heartbeat перед тем как объявить процесс мёртвым.
- **Путаница UTC и локального времени** — таймстамп в имени файла или CSV может быть в UTC, а файловая система Windows показывает локальное время. Разница (например +3ч) выглядит как аномалия, но это не баг.
- **Конфиг с `${ENV_VAR}`-плейсхолдером без проверки `.env`** — незаполненная переменная даёт тихий невалидный результат (`endpoint: null`), а не понятную ошибку. Всегда проверяй `.env` перед разворачиванием конфига.
- **Копирование YAML-полей по аналогии с другой версией проекта** — комбинация полей (`mode: up` + `explicit: [...]`) может работать по-разному в разных версиях. Сначала читай код, который парсит конфиг.
- **Забыть очистку после экспериментов** — одноразовые `.ps1`/`.cmd`/`.py`, Scheduled Tasks и осиротевшие процессы накапливаются на удалённой машине. Это обязательный финальный шаг, не опциональный.
